| 项目 | 内容 |
| --- | --- |
| 文档状态 | 草案，待评审 |
| 适用对象 | 书源作者、规则调试者、`new-book-getter` 兼容开发者 |

## 摘要

本文定义项目所说的 Legado“书源”：它是让客户端按特定请求和规则找到内容的配置，不是网站、下载任务，也不是可用性保证。普通书源 `BookSource` 和订阅源 `RssSource` 是两个并列模型，具有不同的身份、内容单位和读取路径。本文说明怎样选择模型、确定目标能力与实际执行路径、判断结果是否有效，以及在无法验证时怎样报告边界。

按需阅读：[模型与目标](#3-面向使用者的定义) · [使用流程与示例](#5-示例如何编写和判定) · [验证层级](#6-验证与结果报告) · [采用与维护](#7-采用取舍与兼容性)。

## 1. 问题与目标

现有资料中，“有效书源”可能仅指 JSON 可导入，也可能指某条规则有结果，或指一整本书可读取。旧教程、历史技能和近似模拟器还混入互相矛盾的语法及字段要求。没有共同定义时，作者容易补出无用字段，解析器容易把登录页当空结果，测试记录也难以比较。

本 RFC 让读者在不查代码的情况下回答四个问题：这是什么类型的源？本次准备验证什么能力？一次运行应该怎样推进？现有证据最多证明到哪一步？精确字段表、语法分支和当前实现进度分别由[规则索引][I1]、[统一技能的两条工作流](../skills/legado-source/SKILL.md)及[项目能力矩阵](compatibility.md)维护。

本文不发明新的字段或选择器，不规定某个站点的具体规则，也不将 Legado 已定义的能力自动算作 `new-book-getter` 已实现。真实站点会受改版、网络、地区和账号状态影响，不能仅凭静态配置保证持续可用。

## 2. 术语与要求语言

| 术语 | 本文含义 |
| --- | --- |
| 源 | 带身份的配置；包含一个或多个入口、请求条件、提取规则与可选脚本 |
| 目标能力 | 作者或测试者在源 JSON 之外的验证记录中选定的任务，如搜索书籍、取得目录、读取文章或获得文件链接；Legado 没有同名的必填声明字段 |
| 可执行路径 | 由配置、脚本、调用入口和运行时共同决定的实际处理路径；字段存在只提供线索，不等于路径通过 |
| 阶段 | 一次有明确输入和输出的处理，如请求、搜索、详情、目录、正文或 RSS 列表 |
| 规则 | 在某阶段、某输入类型和上下文中求值的表达式；可返回元素、字符串、列表或 URL |
| 上下文 | 求值时可见的搜索词、页码、当前书/章/文章、基址、响应及变量等状态 |
| 验证记录 | 固定源版本、输入、环境和结果，用以限定“通过”声明的范围 |

本文的“**必须**”表示采用本 RFC 时不可违背的互操作或判定约束；“**应**”表示通常遵循、偏离时需要说明原因；“**可以**”表示可选能力。这里使用中文普通含义，并未将这些词声明为 IETF BCP 14 的英文大写关键词；该区分参见[RFC 8174][I4]。

## 3. 面向使用者的定义

### 3.1 先选择模型

| 判断维度 | 普通书源 `BookSource` | 订阅源 `RssSource` |
| --- | --- | --- |
| 身份字段 | `bookSourceUrl` | `sourceUrl` |
| 内容单位 | 书籍、目录、章节、文本或媒体/文件资源 | 文章或媒体条目 |
| 类型字段 | `bookSourceType`：0 文本、1 音频、2 图片、3 文件、4 视频 | `type`：0 网页、1 图片、2 视频 |
| 常见路径 | 搜索或发现 → 详情 → 目录 → 内容 | 分类或搜索 → 列表 → 文章阅读 |

两种模型**必须**分别识别、存档、去重和执行；同一个类型数字不能跨模型解释。身份字段即使允许空字符串，也不代表该源具备有效身份或实际使用价值。

一个源的实体是 JSON 对象。数组可以包装多个实体，但“导入时是否接受单对象、数组或 URL 清单”由具体入口决定；本 RFC 不把某个入口的包装要求变成实体定义。不同导入入口的接受范围仍是[未决问题](#10-未决问题)。

### 3.2 再确定目标能力与执行路径

源**不必**同时具备所有阶段。搜索专用源可以止于书籍信息；文件源可以提供下载地址而无文本正文；RSS 标准 XML 源可以不提供自定义列表选择器。作者或测试者**必须**在源 JSON 之外的验证记录中写明本次目标能力，不能虚构一个 Legado 的“能力声明”字段。该记录说明要验什么，不改变源的执行行为。

执行路径由调用入口和实际配置决定，不能只检查某个规则组是否存在：普通书源的搜索可因 `bookUrlPattern` 进入详情解析分支；脚本源也可能由 `mainJs` 提供能力。只有被实际调用的路径才按其输入、输出及后续导航验收；未测试的路径保持未知。

这带来两条使用规则：

1. 配置字段说明客户端**可能尝试**某条路径，不证明请求、规则或站点当前可用。
2. 存档未知字段**可以**保持 JSON 往返完整；执行器不得因此宣称已支持其语义，遇未实现能力应给出明确结果。

## 4. 参考级行为：源如何运行

一项能力按下列链条求值；下一阶段可以沿用上阶段的 URL、对象和变量。

```text
用户动作或调度
  → 选择入口和上下文
  → 生成请求并取得响应
  → 在当前输入上求值规则
  → 得到阶段结果或可定位的失败
  → 按调用方和本次目标能力判断是否继续验证下一阶段
```

### 4.1 请求与上下文

入口 URL 可以包含搜索词、页码、脚本和请求选项。请求规划后才得到实际方法、地址、请求头、body、编码与 WebView 要求；规则中的相对链接还依赖响应或重定向后的基址。调试时**必须**区分模板文本、发出的请求和收到的页面。`key`、`page` 等绑定由调用场景提供，不能假设每条规则都有相同上下文。

一个 HTTP 成功状态并不保证收到的是预期内容：登录页、验证码页或站点业务错误可能仍以 200 返回。WebView 页面脚本与普通 HTTP 请求也不是“等待更久”的区别。作者应先确认响应的内容类型、编码和实际页面，再修改选择器；兼容实现应将网络、身份/环境与规则失败分开。[I2]

### 4.2 规则求值

Legado 规则有 Default HTML、显式 CSS、JSONPath、XPath、正则、Rhino JS 与网页 JS 等路径。**必须**先按调用入口、输入类型和规则前缀确定模式，再解释选择器、动作和后置替换；不能把整条规则当普通 CSS，也不能简单按 `@`、`||` 或 `##` 全局切分。

对作者最重要的边界如下：

| 情况 | 正确理解 |
| --- | --- |
| Default 中的 `tag.a.0` 等 | Legado 自有的位置/元素语法，不是 CSS 类名 |
| `@CSS:` 下的伪类 | 取决于具体 Jsoup 路径；不存在所有伪类一律禁止的规则 |
| `@html` 与 `@all` | 前者会去除 script/style 后返回外层 HTML，后者保留原外层 HTML |
| `##匹配##替换` 与尾部第四段 | 前者是常规替换；第四段常见为 `###`，只从首个匹配片段求结果，未匹配为空 |
| Rhino 的 `java.*` 与 WebView JS | 两个执行环境，绑定和可用能力不同；脚本存在不表示宿主方法已实现 |

详情及少见组合语法见[语法参考][I3]。本 RFC 不把所有选择器分支重新列为一份易过期的语法手册。

### 4.3 普通书源的阶段结果

各阶段由不同调用方推进；模型字段相同也不意味着输入、结果和失败处理相同。

| 阶段 | 何时使用 | 应得到什么 | 失败边界 |
| --- | --- | --- | --- |
| 搜索或发现 | 源提供相应入口时 | 书籍候选及继续定位所需的信息 | 正常零结果不等于请求失败；可选元数据缺失不应吞掉有效候选 |
| 详情 | 需要补充书籍信息、目录或下载入口时 | 元数据及 `tocUrl` 或文件入口 | 可选字段错误与关键导航失败分开 |
| 目录 | 源提供章节阅读时 | 稳定顺序的章节名、地址与可选状态 | 目录分页去重、防循环；`isVip` 与 `isPay` 分别解释 |
| 正文/资源 | 用户读取章节或媒体时 | 文本、同章后续页或媒体/文件资源 | 资源类型不能一律按文本净化；付费或登录前提单列 |

普通书源的典型路径不是强制模板。`nextTocUrl` 表示目录下一页；`nextContentUrl` 表示**同章正文**的下一页，遇到已知下一章 URL 时本章应停止合并，不能无条件跨到下一章。`sourceRegex` 用于正文获取路径，`replaceRegex` 用于正文合并后的处理，两者不可混成一个步骤。

### 4.4 RSS 订阅源的阶段结果

RSS 的 `ruleArticles` 为空时，标准分支读取 RSS XML 的 `item`；它并非任意 HTML 或 Atom 解析器。配置了 `ruleArticles` 时，自定义分支选择列表项、逐项提取标题、时间、摘要、图片和链接；没有标题的条目会被丢弃。

`ruleNextPage` 是自定义列表分支的**列表下一页**规则；`ruleArticles` 为空时默认 XML 分支直接返回列表和空下一页，不求值 `ruleNextPage`。自定义分支中，值为 `PAGE` 时返回当前分类 URL `sortUrl`，其他值按规则提取。`ruleDescription` 是列表摘要，`ruleContent` 是后续文章阅读路径，二者不互斥。文章的直开、正文分页和图片/视频阅读还取决于源类型、`singleUrl` 及网页环境；列表通过不能推断文章阅读已通过。[I5]

## 5. 示例：如何编写和判定

### 5.1 从需求走到可验证的配置

1. **确定模型与目标能力**：先问结果是书籍/章节，还是订阅文章/媒体；再在验证记录中写明此次只验搜索、列表、目录、正文或哪几项组合。不在 JSON 中增加虚构的能力字段，也不从源类型推断所有阶段都存在。
2. **固定输入证据**：保存源版本、入口、一次脱敏请求及其真实响应；确认方法、重定向、编码、页面类型和登录/WebView 前提。这一步为后面的选择器和相对地址提供基址。
3. **配置最少的阶段**：仅写目标能力需要的入口和规则。列表规则选条目，字段规则在单项上下文求值；每个跳转地址要能定位下一阶段。可选元数据按真实页面提供，不为填满模板而编造。
4. **按阶段验证并停在首个失败处**：先证实请求拿到预期内容，再看规则原始值、最终值和下一阶段地址。若请求或身份前提未过，不把后续规则标为失败；若规则不支持，也不把它解释成正常零结果。
5. **交付限定的结论**：说明哪些阶段在什么环境下通过、哪些字段仅有离线夹具证据，以及仍需真实 App 或账号验证的部分。兼容开发者据此补最小回归和能力矩阵，书源作者据此交付可检查的 JSON。

### 5.2 只支持搜索的普通书源

目标是“输入关键词后列出可定位的书籍”，本例不验目录或正文。以下为**合成离线夹具**，展示 Default HTML 列表规则与预期值，不代表 `example.invalid` 是可访问站点，也不声称已在 Android App 上通过。

源片段（完整导入仍受实际入口与模型字段要求约束）：

```json
{
  "bookSourceUrl": "https://example.invalid",
  "bookSourceName": "合成搜索示例",
  "searchUrl": "https://example.invalid/search?q={{key}}",
  "ruleSearch": {
    "bookList": "class.book",
    "name": "tag.a@text",
    "bookUrl": "tag.a@href"
  }
}
```

固定输入：请求基址为 `https://example.invalid/search?q=demo`，响应正文为：

```html
<div class="book"><a href="/books/1">示例书</a></div>
```

期望：`bookList` 选出一项，该项 `name` 为 `示例书`，链接规则提取的原始值为 `/books/1`；搜索阶段以实际响应基址把 `bookUrl` 解析为 `https://example.invalid/books/1`。这只覆盖合成输入上的搜索提取，不覆盖搜索请求、真实站点、详情、目录或正文。反例：同一输入中的链接若缺失 `href`，即使运行时回退到搜索页基址、且书名存在，也不能把回退地址当成已证实的详情地址，应记录导航字段未通过。

真实站点验收时，关键词有命中应能得到候选和有效定位；关键词无命中时可以正常返回空列表。若响应是 HTTP 403 或登录页，即使规则返回空列表，也只能报告请求/身份边界，不能报告“正常零结果”。其他搜索实现可能走 `bookUrlPattern` 直达详情或脚本路径，不能强制要求本例的 `bookList` 写法。

### 5.3 使用标准 XML 的 RSS 订阅源

目标是“显示订阅条目”。以下同样是**合成离线夹具**；没有发起网络请求，也没有证明 Android App 或 `new-book-getter` 已执行 RSS。源片段故意不设置 `ruleArticles`，从而走标准 XML 分支：

```json
{
  "sourceUrl": "https://example.invalid/feed.xml",
  "sourceName": "合成 RSS 示例",
  "type": 0,
  "ruleNextPage": "PAGE"
}
```

固定输入响应为：

```xml
<rss version="2.0"><channel>
  <item><title>示例文章</title><link>https://example.invalid/articles/1</link></item>
</channel></rss>
```

期望：标准解析分支得到一个标题为 `示例文章`、链接为 `https://example.invalid/articles/1` 的条目，下一页为 `null`。此处即使配置了 `ruleNextPage: "PAGE"` 也不会求值它。反例：将输入换成普通 HTML 列表并仍不设置 `ruleArticles`，不能预期默认分支自动提取 HTML 条目；应判为输入与所选分支不匹配，而非声称站点正常零结果。若文章阅读要在 WebView 中执行脚本，应把“列表可显示”与“文章可阅读”分成两项验证结果。

这两个 JSON 只展示相关字段，不是现成站点源。真实规则必须从目标站点当时的响应和 Legado 的实际执行路径得出。

## 6. 验证与结果报告

“有效”不是一个布尔值。下表是**本项目的报告与验收约定**，不是 Legado 导入器的字段必填清单；模型允许某些空默认值，各导入入口还可能施加不同约束。每项结论**必须**说明模型、JSON 外的目标能力、验证层级和执行路径。[I6]

| 层级 | 本项目通过条件 | 可声称的结果 | 不可据此推断 |
| --- | --- | --- | --- |
| 结构 | JSON 可按选定模型解码；身份字段是非空字符串，且目标入口或执行脚本可识别；记录采用的导入入口 | 该源具备可检查的身份及目标路径线索 | 官方每个入口都接受它；请求或规则可运行 |
| 规则 | 固定输入、输入类型、基址和上下文；目标规则给出预期原始值与最终值，关键导航值可解析 | 指定夹具的指定规则通过 | 当前站点仍可访问；其他规则也通过 |
| 阶段 | 实际请求返回预期类型的内容，并按该执行路径得到可用输出；空结果必须有正确响应与合理零命中证据 | 指定环境中的一次搜索、列表、目录或阅读阶段通过 | 其他阶段通过 |
| 流程 | 在记录环境中连续完成本次目标能力所需阶段及导航；每一跳可追溯 | 该次目标能力通过 | 跨账号、地区、时间永久可用 |

“可用输出”由目标能力界定：搜索候选至少要有可识别名称及下一跳所需地址，除非该路径直接进入详情或由脚本返回结果；目录阅读要能定位章节；RSS 列表要能得到本次要求显示的条目。只查列表时不要求正文。`ruleArticles` 非空的 RSS 分支会丢弃空标题项，默认 XML 分支则按它自己的解析规则处理，不能把该过滤规则跨分支套用。

兼容实现对每个子能力使用 `SUPPORTED`、`PARTIAL`、`UNSUPPORTED`、`UNKNOWN`；`PARTIAL` 写出子集，`UNKNOWN` 不包装成支持。记录至少包括源类型与版本/哈希、测试时间与环境、触发动作、最深成功阶段、首个失败阶段、脱敏的最终请求，以及预期和实际结果。对新增语义，使用最小正例、反例、离线回归；必要时做原版 Android 差分。Python 模拟通过与真实 App 通过分开记录。[I6]

| 观察到的现象 | 此时可作出的判断 |
| --- | --- |
| 请求得到预期页面，列表确实没有条目 | 可以记录该次正常空结果；不能据此证明其他关键词也为空 |
| HTTP 错误、登录页、验证码或业务错误页 | 请求/身份/环境阶段未过；后续选择器结果没有验收意义 |
| 响应正确，但目标元素不存在或提取值不合法 | 记录具体规则与字段失败；可选字段与导航关键字段分开 |
| 脚本调用当前实现没有的宿主方法 | 记录方法名、阶段和 `PARTIAL`/`UNSUPPORTED` 边界，不伪装为空结果 |

## 7. 采用、取舍与兼容性

本 RFC 只统一项目的语言和判断方法，不改变 Legado JSON、现有导入接口或运行时。完整字段和精确语法留给版本化参考资料；项目已实现的子集由[能力矩阵](compatibility.md)持续记录，避免把“官方定义”和“本工程完成度”混成一份文档。

考虑过把普通书源与 RSS 合为单一模型，以及要求所有源具备搜索→详情→目录→正文链路。前者会混淆两套身份和内容单位，后者会错误拒绝搜索专用、文件及媒体源。因此本提案保留两个模型，并按目标能力验收。代价是验证记录需同时注明模型与能力，不能只写“此源通过”。

技能作者应先阅读本 RFC，再按任务进入[统一技能](../skills/legado-source/SKILL.md)的编写或兼容开发参考。文档分工为：固定提交的官方源码确定行为；本 RFC 维护模型、目标能力与验收口径；统一技能的任务参考维护各自任务的操作说明；[能力矩阵](compatibility.md)只报告当前工程的实现状态。遇到行为争议先复查官方执行路径，再同步修订受影响的 RFC 段落与统一技能中的相关引用页。原版或上游版本升级时，必须重新检查受影响的结论和夹具，不能只更新版本号。

## 8. 安全与隐私

源可包含请求头、Cookie、登录脚本、跨域链接和付费动作。测试日志及可提交夹具不得含账号、Token、Cookie、第三方完整书源或作品正文；请求凭据应限制在相应站点及授权场景。规则能求值不赋予登录、支付、发布或删除的权限。验证码和访问限制应作为环境或身份边界报告，不能被无限重试掩盖。

## 9. 决策后的验收标准

本 RFC 被采纳后，一个新书源或兼容性记录至少能回答：模型是什么、JSON 外记录的目标能力是什么、实际走了哪些阶段、首个失败在哪里、证据覆盖到哪一层。统一技能的两条工作流应保持这些术语一致；任何新增功能在能力矩阵中按子能力记录，不以单个站点或下载数量替代规则覆盖。

## 10. 未决问题

1. 单对象、数组和 URL 清单在各官方导入入口中的接受条件和错误形态，仍需逐入口实测。
2. 复杂混合规则、变量生命周期、完整 Rhino 宿主和 WebView 的哪些行为足以形成稳定兼容声明，仍需差分夹具。
3. RSS 已有独立 Java 引擎与 Android 网页层子集，见[能力矩阵](compatibility.md)及[RSS 边界](rss-compatibility.md)；完整网页生命周期、原生回调和媒体行为还需要哪些官方差分证据，仍待逐项确定。
